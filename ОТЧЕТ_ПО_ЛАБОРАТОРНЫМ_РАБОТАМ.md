# ОТЧЕТ ПО ЛАБОРАТОРНЫМ РАБОТАМ

## Лабораторная работа №1: Система планирования проектов с вычислительным клиентом

### 1. Что за задание было

Разработать систему для управления проектными задачами с оптимизацией последовательности выполнения работ. Система состоит из двух компонентов:
- REST API сервер - управление заказами и задачами
- Вычислительный клиент - оптимизация последовательности выполнения задач с учетом ограничений ресурсов и зависимостей между задачами

Цель: найти оптимальную последовательность выполнения задач, минимизирующую общую длительность проекта при ограниченных ресурсах.

### 2. Архитектура решения

Компоненты системы:

1. API Server (порт 8080)
   - REST API для CRUD операций с заказами и задачами
   - In-memory хранилище данных
   - Маршрутизация через Gorilla Mux
   - Поддержка зависимостей между задачами (predecessors)

2. Computational Client
   - API Client - взаимодействие с сервером
   - Scheduler - расчет длительности проекта с учетом ресурсов
   - Optimizer - поиск оптимальной последовательности

Структура данных:
Order
├── Tasks (работы)
│   ├── ID, Name, Duration
│   ├── Resource (количество требуемого ресурса)
│   └── Predecessors (зависимости)

Технологии:
- Go (Golang)
- Gorilla Mux (маршрутизация)
- net/http (HTTP сервер/клиент)

### 3. Ключевые моменты

Алгоритм оптимизации:
- Метод: Перебор случайных последовательностей (Monte Carlo)
- Параллелизм: 8 воркеров обрабатывают задачи одновременно
- Объем: 1,000,000 последовательностей
- Производительность: Прогресс выводится каждые 100,000 итераций

Планирование ресурсов:
- Учет ограничений ресурсов (maxResource)
- Проверка зависимостей между задачами (predecessors)
- Расчет времени начала и окончания каждой задачи
- Определение критического пути

Оптимизации:
- Использование runtime.GOMAXPROCS(runtime.NumCPU()) для максимальной производительности
- Каждый воркер имеет собственный генератор случайных чисел
- Канальная модель для распределения задач между воркерами
- Атомарный поиск лучшего результата

### 4. Итоги

Реализовано:
- REST API для управления заказами и задачами
- Полноценный вычислительный клиент с параллельной обработкой
- Алгоритм оптимизации с учетом ресурсов и зависимостей
- Масштабируемая архитектура клиент-сервер

Результаты:
- Система эффективно находит оптимальную последовательность из миллиона вариантов
- Параллельная обработка на 8 ядрах обеспечивает высокую производительность
- Гибкая модель данных позволяет описывать сложные зависимости задач
- Расширяемая архитектура для добавления новых алгоритмов оптимизации

## Лабораторная работа №2: Микросервисная архитектура с гетерогенными БД

### 1. Что за задание было

Разработать микросервисную систему управления заказами с использованием различных типов баз данных. Каждый сервис должен быть независимым, иметь собственную базу данных и предоставлять REST API.

Требования:
- Использование как SQL (PostgreSQL), так и NoSQL (MongoDB) баз данных
- Изоляция данных между сервисами
- Интеграционное тестирование взаимодействия сервисов
- Docker Compose для оркестрации инфраструктуры

### 2. Архитектура решения

Микросервисы:

1. Product Service (порт 8081)
   - База данных: PostgreSQL
   - Функции: управление каталогом продуктов
   - API: CRUD операции для продуктов

2. Order Service (порт 8082)
   - База данных: MongoDB
   - Функции: управление заказами
   - API: создание и просмотр заказов

3. Inventory Service (порт 8083)
   - База данных: PostgreSQL
   - Функции: управление складом
   - API: учет остатков, обновление наличия

4. Notification Service (порт 8084)
   - База данных: MongoDB
   - Функции: система уведомлений
   - API: создание и просмотр уведомлений

Инфраструктура:
Docker Compose
├── PostgreSQL (порт 5432)
│   ├── Product Service
│   └── Inventory Service
└── MongoDB (порт 27017)
    ├── Order Service
    └── Notification Service

Технологии:
- Go (все сервисы)
- PostgreSQL 15 Alpine
- MongoDB 7
- Docker Compose
- Gorilla Mux

### 3. Ключевые моменты

Принципы микросервисов:
- Database per Service: каждый сервис владеет своей БД
- Service Independence: сервисы развертываются и масштабируются независимо
- Technology Diversity: SQL и NoSQL в одной системе
- API-first: взаимодействие только через HTTP API

Интеграционное тестирование:
- Автоматизированные тесты для каждого сервиса
- Проверка полного сценария: Product → Inventory → Order → Notification
- Проверка доступности, создания, чтения данных
- Подробная отчетность с процентом успеха

Управление данными:
- PostgreSQL для структурированных данных (продукты, склад)
- MongoDB для документо-ориентированных данных (заказы, уведомления)
- Независимые схемы данных для каждого сервиса

Скрипты автоматизации:
- start-services.bat - запуск всей инфраструктуры
- stop-services.bat - остановка и очистка
- run-tests.bat - интеграционные тесты
- test-api.bat - быстрое тестирование API

### 4. Итоги

Реализовано:
- 4 независимых микросервиса с REST API
- Гетерогенная система БД (PostgreSQL + MongoDB)
- Docker Compose для оркестрации
- Полное интеграционное тестирование
- Автоматизация развертывания и тестирования

Достижения:
- Демонстрация паттерна Database per Service
- Успешная интеграция SQL и NoSQL в одной системе
- Масштабируемая архитектура для роста количества сервисов
- Автоматизированное тестирование покрывает полный жизненный цикл

Преимущества архитектуры:
- Независимое развитие и развертывание сервисов
- Возможность выбора оптимальной БД для каждого сервиса
- Изоляция сбоев - падение одного сервиса не затрагивает другие
- Легкое масштабирование отдельных компонентов

## Лабораторная работа №3: Асинхронное взаимодействие через Message Queue

### 1. Что за задание было

Реализовать асинхронное взаимодействие между микросервисами с использованием брокера сообщений RabbitMQ. Система должна обеспечивать:
- Синхронное взаимодействие между Order Service и Inventory Service (HTTP)
- Асинхронную отправку уведомлений через RabbitMQ
- Надежную доставку сообщений с использованием durable queues

### 2. Архитектура решения

Компоненты системы:

1. Order Service (порт 8082)
   - Принимает заказы от клиентов
   - Синхронно проверяет наличие товаров в Inventory Service
   - Синхронно резервирует товары
   - Асинхронно отправляет уведомления в RabbitMQ

2. Inventory Service (порт 8083)
   - Управление складскими остатками
   - API для проверки наличия (/inventory/check)
   - API для резервирования (/inventory/reserve)
   - Синхронные HTTP-ответы

3. Notification Service
   - Consumer сообщений из RabbitMQ
   - Обрабатывает уведомления о созданных заказах
   - Логирует детальную информацию о каждом уведомлении

4. RabbitMQ (порты 5672, 15672)
   - Брокер сообщений
   - Durable queue для надежности
   - Web UI для мониторинга

Паттерны взаимодействия:
Client
  ↓ (HTTP POST)
Order Service
  ↓ (HTTP POST) - синхронно
Inventory Service: check availability
  ↓ (HTTP POST) - синхронно
Inventory Service: reserve items
  ↓ (AMQP) - асинхронно
RabbitMQ Queue
  ↓ (Consumer)
Notification Service

Технологии:
- Go + RabbitMQ AMQP library
- RabbitMQ (Official Docker Image)
- Docker Compose для оркестрации
- HTTP для синхронных операций
- AMQP для асинхронных уведомлений

### 3. Ключевые моменты

Гибридный подход к взаимодействию:
- Синхронное (HTTP): критичные операции (проверка наличия, резервирование)
- Асинхронное (RabbitMQ): некритичные операции (уведомления)

Надежность системы:
- Durable queues - сообщения сохраняются при перезапуске RabbitMQ
- Повторные попытки подключения (10 попыток с интервалом 2 секунды)
- Graceful handling - ошибка отправки уведомления не отменяет заказ
- Таймауты HTTP-клиентов (10 секунд)

Сценарий обработки заказа:
1. Клиент отправляет заказ в Order Service
2. Order Service синхронно проверяет каждый товар в Inventory Service
3. Если все доступно - синхронно резервирует товары
4. Создает заказ в памяти
5. Асинхронно публикует уведомление в RabbitMQ
6. Notification Service получает сообщение и обрабатывает его

RabbitMQ Configuration:
- Queue: order_notifications
- Exchange: default
- Auto-ack: true (для упрощения)
- Durable: true

Мониторинг:
- RabbitMQ Management UI: http://localhost:15672
- Логирование на каждом этапе обработки
- Детальные уведомления с форматированием

### 4. Итоги

Реализовано:
- Гибридная синхронно-асинхронная архитектура
- RabbitMQ для надежной доставки уведомлений
- Проверка и резервирование товаров через HTTP
- Consumer для обработки уведомлений
- Автоматизированные скрипты тестирования

Архитектурные решения:
- Event-Driven Architecture для уведомлений
- Request-Response Pattern для критичных операций
- Decoupling - Order Service не зависит от доступности Notification Service
- Resilience - система устойчива к сбоям отдельных компонентов

Преимущества решения:
- Асинхронность снижает latency для клиента
- Уведомления могут обрабатываться в фоне
- Легко добавить новых подписчиков (consumers)
- RabbitMQ гарантирует доставку даже при временных сбоях

Особенности реализации:
- Graceful degradation - заказ создается даже если уведомление не отправлено
- Retry logic для подключения к RabbitMQ
- Structured logging для отладки
- Durable queues для персистентности

## Лабораторная работа №4: GraphQL Gateway (BFF Pattern)

### 1. Что за задание было

Разработать единую точку входа (API Gateway) для микросервисов, используя GraphQL. Реализовать паттерн Backend for Frontend (BFF), который:
- Объединяет несколько REST API в единый GraphQL endpoint
- Предоставляет гибкий язык запросов для клиентов
- Поддерживает связанные запросы (nested queries)
- Минимизирует over-fetching и under-fetching данных

### 2. Архитектура решения

Компоненты:

1. GraphQL Gateway (порт 8080)
   - Единая точка входа для клиентов
   - Агрегация данных из микросервисов
   - GraphiQL UI для интерактивного тестирования
   - Resolve functions для получения данных из REST API

2. Product Service (порт 8081)
   - REST API для продуктов
   - In-memory хранилище
   - Endpoints: GET /products, GET /products/:id

3. Order Service (порт 8082)
   - REST API для заказов
   - In-memory хранилище
   - Endpoints: GET /orders, GET /orders/:id

Архитектурный паттерн - BFF (Backend for Frontend):
Client (Web/Mobile)
       ↓
GraphQL Gateway (port 8080)
       ├─→ Product Service (port 8081) [REST]
       └─→ Order Service (port 8082) [REST]

GraphQL Schema:
type Product {
  id: String!
  name: String!
  description: String!
  price: Float!
  stock: Int!
}

type Order {
  id: String!
  customerId: String!
  productId: String!
  quantity: Int!
  totalPrice: Float!
  status: String!
  createdAt: String!
  product: Product  # Nested query
}

type Query {
  products: [Product]
  product(id: String!): Product
  orders: [Order]
  order(id: String!): Order
}

Технологии:
- graphql-go/graphql (GraphQL library)
- Go standard library (HTTP client)
- GraphiQL (встроенный UI)
- Docker Compose

### 3. Ключевые моменты

Решение проблемы N+1:
- Реализован resolver для nested field product в типе Order
- Автоматическая подгрузка связанных данных
- Клиент получает все данные одним запросом

Пример мощного запроса:
query {
  orders {
    id
    quantity
    totalPrice
    product {        # Автоматически загружается из Product Service
      name
      description
      price
    }
  }
}

Преимущества GraphQL над REST:
- Гибкость: клиент запрашивает только нужные поля
- Единый endpoint: вместо множества REST endpoints
- Type safety: строгая типизация схемы
- Self-documenting: интроспекция схемы
- Versioning: не требуется версионирование API

Интерактивное тестирование:
- GraphiQL UI встроен в Gateway
- Автодополнение запросов
- Встроенная документация схемы
- Доступно по адресу: http://localhost:8080

Особенности реализации:
- HTTP клиент с таймаутами (10 секунд)
- Обработка ошибок REST API (404, timeouts)
- Поддержка различных форматов данных (map, struct, pointer)
- Логирование GraphQL ошибок

Интеграционные тесты:
- Автоматизированное тестирование GraphQL запросов
- Проверка корректности резолверов
- Тестирование nested queries

### 4. Итоги

Реализовано:
- GraphQL Gateway как единая точка входа
- Агрегация данных из двух REST сервисов
- Nested queries для связанных данных
- GraphiQL UI для интерактивного тестирования
- Автоматизированные интеграционные тесты

Паттерны и практики:
- BFF Pattern - Gateway адаптирован под нужды фронтенда
- API Aggregation - объединение нескольких API в один
- Schema-first Design - чёткая типизированная схема
- Resolver Pattern - декларативная загрузка данных

Решенные проблемы REST:
- Over-fetching (получение лишних данных) → Клиент выбирает нужные поля
- Under-fetching (нужно несколько запросов) → Nested queries в одном запросе
- Множество endpoints → Единый /graphql endpoint
- Версионирование API → Расширение схемы без breaking changes

Преимущества для разработки:
- Frontend разработчики получают гибкий API
- Backend может развиваться независимо
- Gateway изолирует клиентов от изменений в микросервисах
- Легко добавлять новые источники данных

Production-ready фичи:
- Timeouts для предотвращения зависаний
- Error handling на всех уровнях
- Structured logging
- Docker-контейнеризация

## Лабораторная работа №5: Контейнеризация и оркестрация (Docker + Kubernetes)

### 1. Что за задание было

Подготовить микросервисы для production-окружения с использованием контейнеризации и оркестрации. Реализовать две стратегии развертывания:
1. Docker Compose - для локальной разработки и тестирования
2. Kubernetes - для production deployment с автомасштабированием и управлением

Требования:
- Multi-stage Docker builds для оптимизации размера образов
- Health checks для мониторинга состояния
- Автоматический перезапуск при сбоях
- Масштабирование сервисов (реплики)
- Изолированная сетевая инфраструктура

### 2. Архитектура решения

Часть 1: Docker Compose

Структура:
Docker Compose
├── Product Service (port 8081)
│   ├── Dockerfile (multi-stage)
│   ├── Health check
│   └── Auto-restart
└── Order Service (port 8082)
    ├── Dockerfile (multi-stage)
    ├── Health check
    └── Auto-restart

Network: lab5-network (bridge)

Dockerfile Pattern (Multi-stage build):
# Stage 1: Builder
FROM golang:1.21-alpine AS builder
WORKDIR /app
COPY . .
RUN go build -o service main.go

# Stage 2: Runtime
FROM alpine:latest
COPY --from=builder /app/service .
CMD ["./service"]

Docker Compose Features:
- Isolated network (lab5-network)
- Health checks каждые 30 секунд
- Auto-restart (unless-stopped)
- Port mapping для доступа извне

Часть 2: Kubernetes

Архитектура Kubernetes:
Namespace: lab5
├── Product Service
│   ├── Deployment (2 replicas)
│   ├── Service (ClusterIP)
│   ├── Liveness Probe
│   └── Readiness Probe
└── Order Service
    ├── Deployment (2 replicas)
    ├── Service (ClusterIP)
    ├── Liveness Probe
    └── Readiness Probe

Ingress: Маршрутизация внешнего трафика

Kubernetes Resources:

1. Deployments:
   - 2 реплики каждого сервиса для high availability
   - Rolling update strategy
   - Resource limits (CPU: 200m, Memory: 128Mi)
   - Probes для health checking

2. Services:
   - ClusterIP для внутренней коммуникации
   - Port mapping (8081, 8082)
   - Label selectors для роутинга

3. Ingress:
   - Единая точка входа для внешнего трафика
   - Path-based routing
   - Load balancing между репликами

Технологии:
- Docker (контейнеризация)
- Docker Compose (локальная оркестрация)
- Kubernetes (production оркестрация)
- kubectl (управление кластером)
- Docker Desktop Kubernetes (для Windows)

### 3. Ключевые моменты

Multi-stage Docker Builds:
Преимущества:
- Builder stage: полный Go SDK для компиляции
- Runtime stage: минимальный Alpine Linux
- Результат: образ ~10MB вместо ~300MB
- Безопасность: нет компиляторов в production образе

Health Checks в Docker Compose:
healthcheck:
  test: ["CMD", "wget", "--spider", "http://localhost:8081/products"]
  interval: 30s      # Проверка каждые 30 секунд
  timeout: 10s       # Таймаут ответа
  retries: 3         # 3 неудачи = unhealthy
  start_period: 40s  # Grace period при старте

Kubernetes Probes:
livenessProbe:      # Перезапустить pod если не отвечает
  httpGet:
    path: /orders
    port: 8082
  initialDelaySeconds: 30
  periodSeconds: 10

readinessProbe:     # Не направлять трафик пока не готов
  httpGet:
    path: /orders
    port: 8082
  initialDelaySeconds: 5
  periodSeconds: 5

Resource Management в Kubernetes:
resources:
  requests:          # Минимальные требования
    memory: "64Mi"
    cpu: "100m"
  limits:           # Максимальные лимиты
    memory: "128Mi"
    cpu: "200m"

Масштабирование:
# Увеличение количества реплик
kubectl scale deployment product-service --replicas=3 -n lab5

# Kubernetes автоматически:
# - Создает новые pods
# - Регистрирует их в Service
# - Распределяет нагрузку между всеми репликами

Автоматизация развертывания:

Скрипты для Docker:
- build-images.bat - сборка Docker образов
- start-docker.bat - запуск через Compose
- stop-docker.bat - остановка и очистка
- test-docker.bat - тестирование API

Скрипты для Kubernetes:
- check-k8s.bat - проверка готовности кластера
- deploy-k8s.bat - развертывание в кластер
- delete-k8s.bat - удаление всех ресурсов
- test-k8s.bat - тестирование через Ingress

Networking:

Docker Compose:
- Bridge network для изоляции
- Сервисы доступны по имени контейнера
- Port mapping для внешнего доступа

Kubernetes:
- ClusterIP Services для внутренней коммуникации
- DNS-based service discovery
- Ingress для внешнего доступа
- Network policies (опционально)

Реализовано:
- Multi-stage Dockerfiles для оптимизации образов
- Docker Compose для локальной разработки
- Kubernetes Deployments с репликами
- Health checks и auto-restart
- Resource management и limits
- Масштабирование и high availability
- Полная автоматизация развертывания

Docker Compose - Преимущества:
- Простота использования - один файл конфигурации
- Быстрый старт для разработки
- Легко модифицировать и отлаживать
- Идеально для локальной разработки

Kubernetes - Преимущества:
- Production-ready оркестрация
- Автоматическое масштабирование
- Rolling updates без downtime
- Self-healing (автоматический перезапуск)
- Service discovery и load balancing
- Resource management

Production-ready Features:

1. High Availability:
   - 2 реплики каждого сервиса
   - Автоматический failover
   - Load balancing между репликами

2. Observability:
   - Liveness probes для обнаружения зависаний
   - Readiness probes для корректной маршрутизации
   - Health check endpoints

3. Resource Efficiency:
   - Минимальные Docker образы (~10MB)
   - CPU и Memory limits
   - Эффективное использование ресурсов кластера

4. Operability:
   - Автоматизированные скрипты для всех операций
   - Declarative configuration (YAML)
   - Version control для инфраструктуры
   - Rollback возможности

## ЗАКЛЮЧЕНИЕ

В результате выполнения комплекса лабораторных работ была реализована и исследована многоуровневая архитектура распределенных вычислительных систем, демонстрирующая эволюцию от монолитной клиент-серверной модели до полноценной микросервисной архитектуры с применением современных технологий контейнеризации и оркестрации.

Проведенное исследование позволило установить следующие основные результаты:

Во-первых, была продемонстрирована эффективность применения параллельных вычислений для решения задач оптимизации последовательности выполнения работ. Реализованный алгоритм на основе метода Монте-Карло с использованием многопоточности показал возможность обработки больших объемов данных (порядка 10^6 последовательностей) с приемлемой производительностью.

Во-вторых, подтверждена целесообразность применения микросервисной архитектуры для построения масштабируемых распределенных систем. Разработанная система из четырех независимых сервисов продемонстрировала преимущества изоляции данных и независимого развертывания компонентов. Применение гетерогенной модели хранения данных (реляционная и документо-ориентированная СУБД) показало возможность выбора оптимальной технологии для каждого сервиса в зависимости от специфики решаемых задач.

В-третьих, исследованы различные паттерны взаимодействия между микросервисами. Синхронная коммуникация через HTTP протокол продемонстрировала свою эффективность для критичных операций, требующих немедленного ответа. Асинхронная коммуникация через брокер сообщений RabbitMQ показала преимущества для некритичных операций, обеспечивая развязку компонентов и повышая отказоустойчивость системы.

В-четвертых, реализован паттерн Backend for Frontend (BFF) с использованием GraphQL, что позволило решить проблему избыточного и недостаточного получения данных, характерную для REST API. Единая точка входа обеспечила упрощение интеграции клиентских приложений с микросервисной архитектурой.

В-пятых, проведена контейнеризация всех компонентов системы с применением технологии Docker. Использование multi-stage builds позволило оптимизировать размер образов контейнеров. Реализованы два подхода к оркестрации: Docker Compose для локальной разработки и Kubernetes для production-окружения, что подтвердило возможность применения различных инструментов в зависимости от требований к развертыванию.

Практическая значимость выполненной работы заключается в том, что разработанные решения демонстрируют применение современных подходов к проектированию распределенных систем, используемых в индустрии. Реализованная архитектура соответствует принципам Domain-Driven Design, обеспечивает горизонтальное масштабирование и обладает высокой отказоустойчивостью.

Полученные результаты могут быть использованы в качестве основы для разработки более сложных распределенных систем, а также для обучения принципам проектирования микросервисных архитектур. Проведенное исследование подтверждает эффективность применения современных технологий и паттернов проектирования для построения масштабируемых и надежных вычислительных систем.

Перспективы дальнейшего развития включают исследование вопросов распределенных транзакций, реализации паттернов Saga и Circuit Breaker, а также интеграции систем мониторинга и логирования для обеспечения observability распределенных систем.
